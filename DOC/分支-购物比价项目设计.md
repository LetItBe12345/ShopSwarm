12. Jev 的本质其实就是 Local Runtime 的“智能 if-else”

你甚至可以把 Jev 理解成：

传统程序：

Python

    click(search_button)
elif product_visible:
    click(product)
...

问题是现实网页变化太大，你不可能写完这些规则。

所以变成：

Python
运行
action = jev.choose(
    state=page,
    choices=[
        TYPE_TEXT(search_box),
        CLICK(search_button),
        CLICK(product_1),
        CLICK(product_2),
        SCROLL,
        WAIT,
        DONE,
        BLOCKED,
    ],
)

然后：

Python
运行

所以我认为最准确的定义其实是：

Jev 是本地 Browser Runtime 中的 learned policy。

不是 planner。

不是 executor。

不是 orchestrator。

对。JEV 这里真正决定效果的，不是“prompt 写得多长”，而是：

你能不能把当前浏览器状态压缩成一个足够小、但足够做下一步决策的状态。

我会把 JEV 的 context 定义成 6 块。

1. Goal：现在到底要完成什么

不是把整个用户对话塞进去，而是转成结构化目标。

购物场景例如：

JSON
{
  "goal": "找到天猫 Apple 官方店的 iPhone 17 Pro 256GB 黑色版本，并进入商品详情页",
  "constraints": {
    "model": "iPhone 17 Pro",
    "storage": "256GB",
    "color": "black",
    "seller_type": "official",
    "condition": "new"
  },
  "done_when": [
    "商品型号匹配",
    "容量为 256GB",
    "颜色为黑色",
    "店铺为官方店",
    "价格可见"
  ]
}

这里最重要的是 done_when。

因为如果你只给：

find iPhone 17 Pro

JEV 根本不知道：

搜索结果出来算完成？
进入商品详情算完成？
选好 SKU 算完成？
看到价格算完成？

所以：

Goal
≠
自然语言一句话

更应该是：

Goal + Constraints + Completion Criteria

4. Action Space：它到底允许做什么

不要问 Jev：

你下一步想干嘛？

这是开放式生成。

而应该明确：

JSON
{
  "operations": {
    "CLICK": "点击元素",
    "TYPE_TEXT": "填写文本",
    "SELECT": "选择选项",
    "SCROLL": "继续向下",
    "WAIT": "等待页面加载",
    "BACK": "返回上一页",
    "DONE": "目标已经满足",
    "BLOCKED": "无法继续"
  }
}

然后针对每种操作，动态给候选 target。

这点非常重要。

SELECT target head

而不是：

里面随便组合

这样搜索空间小很多。
