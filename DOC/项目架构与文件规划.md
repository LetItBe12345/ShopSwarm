## 2. 插件在整个执行流程中的位置

[打开可交互的动作循环图](diagrams/agent-loop.html)。下面的总流程展示安装层、并行调用及汇总关系。

```mermaid
flowchart TB
    bundle[安装 ShopSwarm Bundle] --> patch[cordis.patch.yml 加载 Host Plugin]
    patch --> register[apply 注册目标级工具和资源清理]
    skill[shopping-research Skill] -. 任务规则 .-> lead[DSH Lead Agent]
    user[用户价格 / 套餐需求] --> lead
    lead --> split[DSH 原生 Subagent 分发]
    split --> a[来源 A Subagent]
    split --> b[来源 B Subagent]
    register -. 提供工具 .-> pa[ShopSwarm 工具调用 A]
    register -. 提供工具 .-> pb[ShopSwarm 工具调用 B]
    a --> pa
    b --> pb
    pa --> la[内层动作循环 A]
    pb --> lb[内层动作循环 B]
    la <--> ba[独立浏览器会话 A]
    lb <--> bb[独立浏览器会话 B]
    la --> ra[报价与证据 / 阻塞或失败原因]
    lb --> rb[报价与证据 / 阻塞或失败原因]
    ra --> a
    rb --> b
    a --> collect[Lead 收集各站结果]
    b --> collect
    collect --> compare[Normalizer / Comparator 做可比性、计算与排序]
    compare --> assess{还需补查且预算允许?}
    assess -->|是| split
    assess -->|否| report[Lead 输出带来源和限制的比较报告]
```

A、B 是同一插件代码的两个调用实例，不要求加载两个插件进程。并发时分别保存任务状态、页面引用和浏览器会话；资源上限由插件管理，Agent 分发与消息传递由 DSH 管理。具体 DSH provider 与工具可见性配置在 M0/M3 验证。

| 部分 | 在执行中的作用 | 不承担的职责 |
|---|---|---|
| Bundle | 包声明与 profile 安装组合 | 不执行页面动作循环 |
| Host Plugin | 注册工具、连接执行模块、管理资源 | 不重写 DSH Agent 主循环 |
| Skill | 按调用方给出的模型和场景拆分任务、调用工具并汇总 | 不直接执行浏览器或计价代码 |
| DSH Lead/Subagent | 高层计划、分发、解释结果、决定补查 | 不必为每次点击重新作高层推理 |
| Jev | 从当前有效集合选择动作和目标 | 不执行 CLI、不独立证明完成 |
| ActionExecutor | 检查目标，将语义动作变为浏览器操作 | 不决定比较哪个模型或提供方 |
| Verifier | 核对完成条件和字段证据 | 不把模型的 DONE 当作证据，不做额度换算 |

插件通过 DSH 工具执行位置进入外层循环。它不是每一轮都必须触发的全局 hook。外层一次调用 `browser_do`，内部可以执行多轮页面动作；结束后，DSH 将工具结果用于下一次高层判断。工具名称均为拟定名称。

## 3. 一次 browser_do 内部怎样循环

```mermaid
flowchart TD
    start[输入目标、约束与完成条件] --> session[取得本任务会话与取消信号]
    session --> observe[读取当前页面快照并更新引用]
    observe --> context[组织目标、进度、页面、近期结果与有效动作集]
    context --> jev[Jev 选择动作及目标]
    jev --> kind{动作类型}
    kind -->|普通动作| guard[检查目标属于当前快照且允许操作]
    guard -->|通过| text[填写文本优先来自任务；必要时文本模型补全]
    text --> execute[ActionExecutor 调用 agent-browser]
    execute --> update[记录结果；新页面观察后更新进度]
    update --> observe
    guard -->|引用失效| observe
    kind -->|DONE| verify[抽取候选报价并独立检查完成条件]
    verify -->|证据不足但可继续| observe
    verify -->|通过| success[成功结果：报价、证据与未知字段]
    kind -->|BLOCKED| blocked[阻塞结果：原因与当前进度]
    kind -->|服务失败或取消| failed[未完成结果：原因与已有证据]
    cancel[任意阶段取消、超时或异常] --> failed
    success --> cleanup[finally：释放本次调用所属资源]
    blocked --> cleanup
    failed --> cleanup
    cleanup --> result[结果返回调用它的 DSH Agent]
```

建议首版让一次工具调用拥有一次会话，调用结束就释放，减少跨调用资源管理。跨调用续用会话是否必要应在真实任务验证后决定。释放失败需报告清理错误，不能静默宣称资源已全部关闭。

循环中保存的核心数据是：

- `Task`：目标、来源范围、约束和完成条件。Coding Plan 方向后续区分 requiredFields 与 desiredFields。M2 暂不设置任务级执行预算。
- `PageState`：URL、页面摘要、当前元素表及引用版本。页面文本是数据，不能改变任务规则。
- `Progress`：由当前证据支持的已完成字段；页面或套餐语义变化后重新核对，不永久相信历史状态。
- `ActionResult`：成功、失败或结果不确定，以及近期变化。结果不确定时先观察，不能直接重复点击。
- `Offer + Evidence`：M2 当前仍是历史报价结构。M4 的 PlanOffer 需要 provider、plan、model、billing、priceType、quota、条件、来源、采集时间和逐字段证据。

例如任务是“核对某模型的 Coding Plan Pro 月费、支持模型和周额度”：Jev 可以依次打开价格页、切换套餐卡片或展开额度说明；每个动作后重新读取页面。Jev 选择 DONE 后，Verifier 仍要核对 provider、plan、price、billing period 和任务要求的字段。页面没有公开周额度时，如果它是 desired 字段就保留 unknown；如果是 required 字段则任务不能成功。

## 4. 工具输入输出建议

`browser_do({ goal, constraints, doneWhen, site })` 完成一个可验证的站点任务。Agent 身份和取消信号应从 DSH 执行上下文取得，不让模型伪造资源归属。

返回建议包含 `status`、`offers`、`evidence`、`progress`、`reason` 和 `metrics`。状态至少区分成功、阻塞、失败与取消。若宿主取消导致工具结果无法投递，也应完成本地资源释放和脱敏记录，不能保证取消后仍有正常 tool result。

`plan_compare({ offers })` 是 M4 的规划入口：先判断 provider/plan/model/billing/priceType/quota 是否可比，再做确定性计算和排序。它不调用浏览器；需要补查时由 Lead 再发起来源任务。单来源失败不抹掉其他来源的有效记录。

首版只排序通过 comparability 检查的同币种、同价格语义记录。Token/request/credit、不同额度窗口、首购/续费、条件折扣和 unknown 默认单独说明，不为了产生最低价强行换算。
