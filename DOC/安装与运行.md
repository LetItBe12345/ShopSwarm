# 安装与运行

本页记录开发安装、诊断和独立 DSH profile 验收方式。ShopSwarm 面向通用自然语言购物研究；Coding Plan、LLM API 套餐和第三方中转套餐是测试域之一。浏览器工具用于公开商品、价格、套餐页面和本地验收，GLM-5.3 只出现在测试样例里。

## 版本

- Node.js：24.21.0
- pnpm：11.7.0
- DSH：0.1.7-alpha.2
- agent-browser：0.38.1

仓库通过 `.node-version`、`.nvmrc` 和 `package.json` 固定 Node.js 与 pnpm 版本。本机使用 nvm 时，进入仓库后先运行 `nvm use`，再运行 `corepack enable`；确认 `node --version` 为 `v24.21.0`、`pnpm --version` 为 `11.7.0` 后再执行：

```bash
pnpm install --frozen-lockfile
pnpm check
pnpm smoke:browser
```

`pnpm check` 执行源码及脚本类型检查、单元测试和构建。`pnpm smoke:browser` 启动仅监听 `127.0.0.1` 的临时页面，通过 DSH ToolRuntime 调用 `shopswarm_diagnose`，依次打开页面、读取快照和关闭独立会话。

## GitHub Actions

`.github/workflows/ci.yml` 在 PR、`main` push 和 Release 发布时运行离线检查：安装固定版本 Node.js、pnpm、agent-browser 和 Chrome，执行 `pnpm check` 与 `pnpm smoke:browser`。`pnpm test` 已包含纯函数测试、可控模型响应测试、真实浏览器访问本地固定页面的测试。`tests/provider-benchmark.e2e.test.ts` 的两个来源是本机模拟服务，不代表真实厂商。

Release 发布后，`release_live` 任务还会执行 `pnpm smoke:shopping`：浏览器访问本地固定页面，并调用真实 Jev 和 DeepSeek API，验证当前单站任务的动作选择、字段提取和证据检查。此任务不访问真实市场来源，也不验证市场价格；发布前的真实来源验收仍按 Q.1、M4.3 和《真实购物任务与测试策略》的多领域矩阵另行执行。Release 工作流在发布事件之后运行，失败不会阻止 Release 创建。

在 GitHub 仓库创建 `release-e2e` Environment，并在其中配置 `JEV_API_KEY` 与 `DEEPSEEK_API_KEY` 两个 Secret。PR 和 `main` 的离线任务不读取这两个 Secret。真实调用只在 Release 事件触发，会产生 API 用量；不要把响应正文、页面快照或浏览器 Profile 上传为公开构建产物。

## Bundle 和 Host Plugin

`package.json` 的 `dsh.bundle.patch` 指向 `cordis.patch.yml`。补丁向已有 DSH profile 加入 `shopswarm` Host Plugin。插件入口是 `dist/index.js`，注册诊断工具 `shopswarm_diagnose`、手动浏览工具 `shopswarm_browse` 和单站研究工具 `shopswarm_research`。后者需要 `JEV_API_KEY` 和 `DEEPSEEK_API_KEY`；Jev 中转站配置见 [Jev 中转站使用](Jev中转站使用.md)。

M0.3 已通过临时 `DSH_HOME` 验证从本地 tarball 安装、真实自然语言 Agent 调用、正常/失败/取消清理和移除。该流程不会修改用户已有的 DSH profile。

M3.1 后，ShopSwarm 在单个 DSH 进程内默认同时运行最多 2 个浏览器工具调用。需要改变上限时，在所用 profile 的 `cordis.patch.yml` 覆盖插件配置，例如：

```yaml
- id: shopswarm
  config:
    maxConcurrentBrowserTasks: 1
```

超出上限的调用等待，等待时取消会退出队列。一次 `shopswarm_research` 在重开复核时可能短暂持有两个浏览器会话；这个参数限制工具调用数。一次性 DSH `headless` 多来源任务让 `subagent` 使用 `run_in_background: false`，Lead 才能在当前进程结束前收取结果。完整分发要求见随包提供的 `shopping-research` Skill。

## M0 阶段验收

真实模型验收需要 DeepSeek API Key。只把密钥写入已被 Git 忽略的仓库根目录 `.env`：

```dotenv
DEEPSEEK_API_KEY=你的密钥
```

不要把 `DEEPSEEK_BASE_URL` 写入 `.env`。DSH 把它视为启动环境控制项；本项目使用 DeepSeek 官方默认地址 `https://api.deepseek.com`。需要覆盖地址时，只能由启动环境显式导出。官方地址依据见 [DeepSeek API 文档](https://api-docs.deepseek.com/quick_start/pricing/)。

## 社区 TUI 本地试用

2026-09-23 在独立 worktree `/home/jin/开源/ShopSwarm-tui` 的 `runtime/dsh-tui/home` 安装了社区插件 [`@nexlineai/dsh-tui` 0.1.2](https://github.com/nexlineai/dsh-tui)。该版本是社区包，不是 DSH 官方随附的 TUI。这个 `DSH_HOME` 和打包文件都在 Git 忽略的 `runtime/` 下；原有 `~/.dsh` 未用于这次安装。

本机已有可运行的配置。在该 worktree 中启动：

```bash
export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"
./scripts/run-dsh-tui.sh
```

启动脚本从 worktree 的 `.env` 读取 `DEEPSEEK_API_KEY`，清除 DSH 与 agent-browser 的代理变量，并使用独立的 TUI profile。需要调用 `shopswarm_research` 时，`.env` 还需有 `JEV_API_KEY`。`.env` 不提交到 Git。终端必须支持交互式 TTY；退出可按 `Ctrl+D`。

安装过程：先用本仓库的 Node.js 24.21.0 和 pnpm 11.7.0 安装项目依赖、构建并打包 ShopSwarm，再把 `@nexlineai/dsh-tui@0.1.2` 和本地 `shopswarm-0.0.0.tgz` 安装进同一个 `tui` profile。Profile 的 `pnpm-workspace.yaml` 允许 `agent-browser` 构建脚本。当前机器的 DSH 插件管理命令实际调用 pnpm 9.15.9；安装时报告 TUI 所依赖的 DSH `0.1.0-rc` 包与 ShopSwarm 固定的 `0.1.7-alpha.2` peer 版本不一致。因此这只是已实测的本机组合，不能据此声明跨版本兼容。

本次 TUI 端到端连通测试以 `tty: true` 启动全屏 TUI，通过真实 DeepSeek Agent 发送一次自然语言请求，让它调用 `shopswarm_diagnose(checkBrowser: true)`。这验证 TUI/Agent/工具/浏览器链路，不属于真实购物来源 E2E。TUI 显示工具调用和结果，工具在独立 headless 后台浏览器中访问 `https://example.com/`，快照命中 `Example Domain`，结果为 `status: ok`、`markerFound: true`。记录时间为 2026-09-23 21:50（Asia/Shanghai）；这一回合约 4 秒。退出后 `agent-browser session list --json` 返回空会话。本次终端没有 `DISPLAY`，因此无法测量前台焦点是否变化。测试没有调用 `shopswarm_research`，也没有验证真实 Coding Plan 价格页。

## 代理

ShopSwarm 启动 DSH 和 agent-browser 时不配置代理。当前终端可以保留自己的 `HTTP_PROXY`、`HTTPS_PROXY` 或 `ALL_PROXY`；这两个进程不继承它们。

原因：

- DSH 调用的是 DeepSeek 官方 API，地址是 `https://api.deepseek.com`。DSH 0.1.7-alpha.2 会把标准代理变量用于模型请求。本项目不走这层代理。
- agent-browser 0.38.1 在未设置 `AGENT_BROWSER_PROXY` 时，会依次读取 `HTTP_PROXY`、`http_proxy`、`HTTPS_PROXY`、`https_proxy`、`ALL_PROXY`、`all_proxy`，并传给 Chrome 的 `--proxy-server`。价格页和本地验收页面都不该进入这台终端的代理。
- 真实 E2E 不绑定某类商城或 Coding Plan。默认选择公开、无需登录、风控较低的来源；代理会改变页面和耗时，不能静默当作本项目默认出口。高风控商城可作为兼容性记录或人工扩展测试。

实现上，ShopSwarm 在创建这两个子进程的环境时删除上述变量，以及 `FTP_PROXY`、`ftp_proxy`、`NO_PROXY`、`no_proxy`、`AGENT_BROWSER_PROXY` 和 `AGENT_BROWSER_PROXY_BYPASS`。测试和验收脚本也使用去掉代理后的环境。`pnpm install` 不在这条策略里，仍使用当前终端环境。

当前 Jev 默认使用兔子 API `https://api.tu-zi.com/v1/systemone`，模型为 `jev-1.13`，从本机 `.env` 或进程环境读取 `JEV_API_KEY`。配置和脱敏连通命令见 [Jev 中转站使用](Jev中转站使用.md)。该地址是 Jev 的调用通道，不是被比较的价格来源。不要把终端代理写成 Jev 的默认配置。

执行：

```bash
pnpm install --frozen-lockfile
pnpm check
pnpm acceptance:m0
pnpm benchmark:cases
```

`pnpm benchmark:cases` 只连接 `127.0.0.1` 上的两个模拟来源，打印评分、延迟、Token 和费用是否已知。它不调用真实厂商，输出里的金额是夹具单价，不是市场价格。

`pnpm acceptance:m0` 会：

1. 在系统临时目录创建独立 `DSH_HOME` 和 `headless` profile。
2. 构建并打包当前 ShopSwarm，通过 profile 自己的 pnpm 安装 tarball。
3. 明确允许 agent-browser 的安装脚本，不依赖全局安装。
4. 启动本地固定页面，通过真实 DeepSeek Agent 自然语言调用 `shopswarm_diagnose`。
5. 验证正常、工具失败和 SIGINT 取消后的资源清理，并确认外部 agent-browser 会话保持存活。
6. 移除 ShopSwarm，确认 profile 清单不再包含本包且 DSH 仍能启动，最后删除临时目录。

验收会产生真实 API 用量。输出只保留布尔验收结果，不记录 API Key、模型推理文本、Cookie 或 Profile。

## 用户数据位置

ShopSwarm 遵循 XDG 基础目录。未设置对应环境变量时使用：

- 配置：`~/.config/shopswarm`
- 状态和脱敏运行记录：`~/.local/state/shopswarm`
- 可删除缓存：`~/.cache/shopswarm`

测试和运行不得把数据写入 `可参考项目/`。浏览器连通测试使用临时、无登录的 agent-browser 会话，不读取用户正在使用的 Chrome Profile。

ShopSwarm 的一次性诊断会话使用单独的 socket 目录。正常路径通过 `finally` 关闭；宿主中断时，会话专属看门进程核对 PID 的会话名和 socket 目录后补做释放，不使用 `close --all`。
