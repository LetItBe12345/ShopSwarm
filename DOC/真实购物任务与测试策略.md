# 真实购物任务与测试策略

日期：2026-09-23。状态：当前产品与测试基线。

## 1. 输入边界

ShopSwarm 面向自然语言购物任务。用户描述想买什么、约束是什么、希望比较哪些信息即可。输入不要求先转换成 Coding Plan、固定商品模型或固定平台格式。

典型输入可以是：

- “找一台 27 英寸、2K、预算 2000 元以内的显示器，比较几个公开来源。”
- “比较几家公开页面上的 2TB SSD 价格和保修条件。”
- “比较几个支持某模型的 Coding Plan，保留套餐价格和额度规则。”

Lead Agent 负责把自然语言意图转成可执行的来源子任务。Jev 只处理单个页面上的受约束动作选择，不负责决定用户应该买什么，也不负责金额计算和最终排序。

## 2. 测试层级

测试分四层，不能用其中一层替代另一层。

1. **离线单元测试**：数据结构、证据校验、comparability、失败分类、取消和资源释放。
2. **本地浏览器 fixture**：动作、等待、页面变化、失效引用、动态选择、遮挡、伪 DONE、prompt injection。
3. **单来源真实 E2E**：真实公开页面 + 真实浏览器 + 真实 Jev / 提取模型，验证从自然语言子任务到证据化结果的整条链路。
4. **多来源真实 E2E**：同一个自然语言购物意图分发到多个来源，保留成功、失败和 unknown，再由确定性代码比较真正可比的结果。

本地 fixture 不能被描述成真实市场覆盖；真实页面失败也不能靠 fixture 抵消。

## 3. 真实 E2E 覆盖矩阵

首版至少覆盖三类任务：

| 任务域 | 目的 | 最低覆盖 |
|---|---|---|
| 数字服务 / Coding Plan | 覆盖套餐、周期、额度、条件价格等复杂语义 | 1 个自然语言任务，至少 2 个公开来源 |
| 消费电子 | 覆盖型号、规格、卖家、价格和页面选择状态 | 1 个自然语言任务，至少 2 个公开来源 |
| 其他实体商品或消费品 | 验证实现没有偷偷依赖“模型/Token/套餐”语义 | 1 个自然语言任务，至少 2 个公开来源 |

来源应尽量跨不同站点结构。不要只在同一站点换三个 URL 后声称完成跨平台验证。

Coding Plan 是矩阵中的一行，不是整个矩阵。

## 4. 来源选择

真实 E2E 优先使用：

- 无需登录即可读取核心商品或套餐信息的公开页面；
- 页面结构能由普通浏览器正常访问；
- 不要求验证码、短信、滑块或账户态才能看到基础价格；
- 可以在测试后独立重开并再次核对。

对于京东、淘宝、天猫等当前已观察到高频风控或登录墙的来源，不把它们设为默认 CI / 验收来源。它们可以保留为兼容性记录或人工扩展测试。

这里的“避开”是**选择更适合自动化验收的公开来源**，不是绕过站点安全措施。

## 5. 用例记录格式

每次真实 E2E 至少记录：

- 原始自然语言任务；
- 任务拆出的约束和需要核对的字段；
- 来源 URL 与来源名称；
- 采集时间；
- 浏览器/Jev/提取模型版本或配置；
- 成功、失败、阻塞或取消；
- unknown 字段；
- 证据摘录；
- 独立重开验证结果；
- 总耗时和主要阶段耗时；
- 是否出现登录、验证码、频控或页面结构异常。

价格是当次观察值，不把静态数字提交成长期“正确答案”。

## 6. Coding Plan fixture 的位置

[Coding Plan 比价规则](Coding%20Plan%20比价规则.md) 继续保留，因为它提供了很好的复杂价格语义测试：首购/续费、月付/年付、Token/request/credit、额度窗口、倍率和 unknown。

这些规则应实现为通用字段与领域扩展的测试，而不是反过来把 ShopSwarm 的核心任务模型变成 `PlanOffer`。

## 7. 当前实现边界

当前 `shopswarm_research` 仍是 M2 单来源兼容接口，参数是 `startUrl + goal + model + specs + seller`。这能验证“已知目标页面上的已知对象”，但还不是完整的自然语言购物入口。

自然语言入口目前由 DSH / Skill 负责解释和拆分。后续 M4 需要把“任务字段”和“报价字段”从 Coding Plan / 商品型号中抽象出来，使多来源结果可以在不同购物域复用同一套证据与 comparability 逻辑。
